# Speechara Live Translation v2 Backend Contract

## 1. Goal

Provide a low-latency, reconnect-safe live translation protocol for the macOS client without changing the existing Web or Windows endpoints.

The v2 protocol separates disposable live previews from durable final translations:

- A preview must always favor the newest recognized text and may be cancelled or dropped.
- A final turn must be translated exactly once logically, retried safely, and remain resumable after reconnect.
- Responses from an obsolete connection or an obsolete client revision must never overwrite newer text.

## 2. Endpoint

```text
GET wss://<backend>/api/v2/ai/translation/live
```

The existing endpoint remains unchanged:

```text
/api/ai/translation/live
```

Only macOS uses v2 during the initial rollout.

## 3. Authentication

Use the same authentication accepted by the current Speechara WebSocket endpoints:

```http
Authorization: Bearer <access-token>
Cookie: speechara_refresh_token=<refresh-token>
Origin: <configured-speechara-origin>
```

Backend requirements:

1. Authenticate before accepting application messages.
2. Bind every live session to the authenticated account ID.
3. A client may resume only a session owned by the same account.
4. Never expose DeepSeek credentials to the client.
5. Close unauthorized connections with a policy/auth close code and a structured `error` message when possible.

## 4. Transport

- WebSocket text frames containing UTF-8 JSON.
- One logical translation session may survive multiple WebSocket connections.
- One WebSocket handles both preview and final messages.
- Backend sends `ping` or WebSocket ping frames at least every 15 seconds when otherwise idle.
- Client may send `ping`; backend responds with `pong`.
- Unknown message fields must be ignored for forward compatibility.
- Unknown message types return `unsupported_message` without closing the connection.

## 5. Identifiers and ordering

### sessionId

UUID generated by the client for one listening session. It remains unchanged across reconnects.

### connectionId

UUID generated by the backend for each accepted WebSocket connection. Every server message after `ready` includes it.

When a new connection resumes a session, the previous connection is obsolete. Work may finish internally, but results from its old `connectionId` must not be emitted to the new connection unless they are durable final results reconciled through session state.

### turnId

UUID generated by the client for one logical source-language utterance.

### clientRevision

Monotonically increasing positive integer scoped to `(sessionId, turnId)`.

- Every newer source-text snapshot increments `clientRevision`.
- Backend echoes it in acknowledgements and results.
- A result for revision N must never replace revision N+1.
- Duplicate messages with the same identity and payload are idempotent.

### serverRevision

Monotonically increasing positive integer scoped to `(sessionId, turnId, clientRevision)` and generated by the backend when the model streams or refines output.

## 6. Connection lifecycle

### 6.1 Server hello

Immediately after authentication:

```json
{
  "type": "hello",
  "protocolVersion": 2,
  "connectionId": "b9ab52a7-9808-46d4-b8cf-f4c134b242a2",
  "serverTime": "2026-07-21T14:20:00.123Z",
  "capabilities": {
    "previewCancellation": true,
    "finalResume": true,
    "streamingRevisions": true
  }
}
```

### 6.2 Configure a new session

Client:

```json
{
  "type": "configure",
  "protocolVersion": 2,
  "sessionId": "7bccb395-93db-49f5-ae94-78c6d8215a99",
  "sourceLanguage": "en",
  "targetLanguage": "ru",
  "client": {
    "platform": "macos",
    "appVersion": "1.2.3",
    "build": "456"
  }
}
```

Backend validates languages, creates session state, and replies:

```json
{
  "type": "ready",
  "protocolVersion": 2,
  "sessionId": "7bccb395-93db-49f5-ae94-78c6d8215a99",
  "connectionId": "b9ab52a7-9808-46d4-b8cf-f4c134b242a2",
  "resumed": false
}
```

No translation message is accepted before `ready`.

### 6.3 Resume

Client reconnects using the same `sessionId`:

```json
{
  "type": "resume",
  "protocolVersion": 2,
  "sessionId": "7bccb395-93db-49f5-ae94-78c6d8215a99",
  "sourceLanguage": "en",
  "targetLanguage": "ru",
  "pendingFinals": [
    {
      "turnId": "941394ca-6483-4aaa-a422-4c471d2afe8d",
      "clientRevision": 8
    }
  ]
}
```

Backend replies with `ready`, `resumed: true`, then sends the known state for each requested final:

- `translation_final` when complete;
- `final_ack` with `status: queued` or `processing` when still pending;
- `final_missing` when backend has no durable record and client must resend the full final source text.

## 7. Preview flow

### 7.1 Client request

```json
{
  "type": "translate_preview",
  "sessionId": "7bccb395-93db-49f5-ae94-78c6d8215a99",
  "turnId": "941394ca-6483-4aaa-a422-4c471d2afe8d",
  "clientRevision": 7,
  "sourceText": "We should move this ticket to the next release",
  "sentAt": "2026-07-21T14:20:01.300Z"
}
```

### 7.2 Preview acknowledgement

Backend acknowledges receipt immediately, before calling DeepSeek:

```json
{
  "type": "preview_ack",
  "sessionId": "7bccb395-93db-49f5-ae94-78c6d8215a99",
  "connectionId": "b9ab52a7-9808-46d4-b8cf-f4c134b242a2",
  "turnId": "941394ca-6483-4aaa-a422-4c471d2afe8d",
  "clientRevision": 7,
  "status": "accepted"
}
```

Allowed statuses:

- `accepted`
- `superseded` — a newer revision is already known
- `rate_limited` — preview was dropped; final flow remains available

### 7.3 Latest-wins semantics

For each `(sessionId, turnId)`:

1. Keep at most one waiting preview: the newest revision.
2. When revision N+1 arrives, mark N obsolete immediately.
3. If provider cancellation is available, cancel N.
4. If provider cancellation is unavailable, allow N to finish but discard its output before emission.
5. Never retry a preview after timeout, provider failure, reconnect, or cancellation.
6. Preview failure must never pause or close the final translation lane.
7. Preview processing must not block another turn's final translation.

### 7.4 Preview result

```json
{
  "type": "translation_preview",
  "sessionId": "7bccb395-93db-49f5-ae94-78c6d8215a99",
  "connectionId": "b9ab52a7-9808-46d4-b8cf-f4c134b242a2",
  "turnId": "941394ca-6483-4aaa-a422-4c471d2afe8d",
  "clientRevision": 7,
  "serverRevision": 1,
  "text": "Нам следует перенести этот тикет в следующий релиз",
  "isFinal": false,
  "timing": {
    "queueMs": 3,
    "providerFirstTokenMs": 210,
    "providerTotalMs": 390,
    "totalMs": 398
  }
}
```

If streaming output is supported, multiple messages may be sent with increasing `serverRevision`. The text is a complete replacement snapshot, not a delta.

Backend must check immediately before every emission that this is still the newest `clientRevision` and the current connection is still active.

## 8. Final flow

### 8.1 Client request

```json
{
  "type": "translate_final",
  "sessionId": "7bccb395-93db-49f5-ae94-78c6d8215a99",
  "turnId": "941394ca-6483-4aaa-a422-4c471d2afe8d",
  "clientRevision": 8,
  "sourceText": "We should move this ticket to the next release.",
  "sourceTimestamp": "2026-07-21T14:20:01.000Z",
  "sentAt": "2026-07-21T14:20:02.000Z"
}
```

### 8.2 Durable acknowledgement

Backend must persist or durably enqueue the final before replying:

```json
{
  "type": "final_ack",
  "sessionId": "7bccb395-93db-49f5-ae94-78c6d8215a99",
  "connectionId": "b9ab52a7-9808-46d4-b8cf-f4c134b242a2",
  "turnId": "941394ca-6483-4aaa-a422-4c471d2afe8d",
  "clientRevision": 8,
  "status": "queued"
}
```

Allowed statuses:

- `queued`
- `processing`
- `completed`
- `duplicate`

The idempotency key is:

```text
accountId + sessionId + turnId + clientRevision + type(final)
```

### 8.3 Final ordering and retries

1. Finals are durable and must survive WebSocket disconnects and backend worker restarts.
2. Retry recoverable provider errors with exponential backoff and jitter.
3. Recommended retry schedule: 250 ms, 750 ms, 2 s, 5 s, then background retry.
4. A final for one turn must not be blocked by preview requests.
5. Preserve source turn order when emitting finals to the client. Internally, processing may be concurrent.
6. Do not silently drop a final.
7. If permanently failed, persist the failure and send `final_failed` on the active connection or during resume.

### 8.4 Final result

```json
{
  "type": "translation_final",
  "sessionId": "7bccb395-93db-49f5-ae94-78c6d8215a99",
  "connectionId": "b9ab52a7-9808-46d4-b8cf-f4c134b242a2",
  "turnId": "941394ca-6483-4aaa-a422-4c471d2afe8d",
  "clientRevision": 8,
  "serverRevision": 1,
  "text": "Нам следует перенести этот тикет в следующий релиз.",
  "isFinal": true,
  "timing": {
    "queueMs": 4,
    "providerFirstTokenMs": 230,
    "providerTotalMs": 510,
    "totalMs": 520
  }
}
```

The final result replaces every preview for the same `turnId`.

## 9. Context management

Backend maintains short finalized context per session:

- Use only completed final source/translation pairs as model history.
- Never add previews to durable context.
- Keep the last 4 completed turns by default.
- Context is ordered by source turn sequence, not provider completion time.
- A reconnect must not duplicate context entries.
- A new session starts with empty context unless an explicit history payload is provided.

The translation prompt must request only the translated text, preserve timestamps and speaker labels, and prohibit commentary.

## 10. Backpressure and limits

Recommended defaults per account/session:

- Maximum preview input: 4,000 UTF-8 characters.
- Maximum final input: 8,000 UTF-8 characters.
- Maximum active preview provider request: 1 per turn and 2 per session.
- Maximum active final provider requests: 2 per session.
- Maximum queued previews: 1 per turn; newest replaces older.
- Maximum queued finals: 200 per session before explicit `over_capacity` failure.
- Preview rate target: up to 4 messages/second per session; coalesce above this rate.
- Session retention after disconnect: at least 15 minutes.
- Completed final retention: at least 24 hours or the lifetime of persisted meeting history.

Rate limiting previews must never disable final requests.

## 11. Errors

Generic recoverable error:

```json
{
  "type": "error",
  "sessionId": "7bccb395-93db-49f5-ae94-78c6d8215a99",
  "connectionId": "b9ab52a7-9808-46d4-b8cf-f4c134b242a2",
  "code": "provider_timeout",
  "message": "Translation provider did not respond in time.",
  "recoverable": true,
  "scope": "preview",
  "turnId": "941394ca-6483-4aaa-a422-4c471d2afe8d",
  "clientRevision": 7
}
```

Required error codes:

- `unauthorized`
- `invalid_message`
- `unsupported_protocol`
- `unsupported_message`
- `session_not_found`
- `session_conflict`
- `invalid_revision`
- `payload_too_large`
- `rate_limited`
- `over_capacity`
- `provider_timeout`
- `provider_unavailable`
- `final_failed`
- `internal_error`

`scope` is one of `connection`, `session`, `preview`, or `final`.

Preview errors are non-fatal. Session/connection errors may close the socket. Final errors must be durable and resumable.

## 12. Ping and graceful close

Client ping:

```json
{
  "type": "ping",
  "clientTime": "2026-07-21T14:20:10.000Z"
}
```

Server:

```json
{
  "type": "pong",
  "connectionId": "b9ab52a7-9808-46d4-b8cf-f4c134b242a2",
  "clientTime": "2026-07-21T14:20:10.000Z",
  "serverTime": "2026-07-21T14:20:10.030Z"
}
```

Graceful session completion:

```json
{
  "type": "complete_session",
  "sessionId": "7bccb395-93db-49f5-ae94-78c6d8215a99"
}
```

Backend stops previews, finishes all acknowledged finals, and replies:

```json
{
  "type": "session_completed",
  "sessionId": "7bccb395-93db-49f5-ae94-78c6d8215a99",
  "pendingFinalCount": 0
}
```

If finals remain, return their count and continue processing them durably. Client may disconnect and retrieve them by resume/history synchronization.

## 13. Observability

Every backend log entry for v2 should include when applicable:

- accountId
- sessionId
- connectionId
- turnId
- clientRevision
- serverRevision
- messageType
- preview/final lane
- queueMs
- providerFirstTokenMs
- providerTotalMs
- totalMs
- provider request ID
- cancellation reason
- reconnect/resume result
- retry attempt
- final idempotency key or hash

Do not log full meeting text by default. Log character count and a non-reversible or access-controlled hash. Full text logging must require an explicit temporary diagnostic flag.

Metrics:

- preview latency p50/p95/p99
- final latency p50/p95/p99
- preview superseded count
- preview timeout/error count
- final retry/failure count
- reconnect count
- resume success/missing count
- stale emission prevented count
- active sessions and queue depth

## 14. Performance targets

Measured backend-side, excluding client audio/STT latency:

- `preview_ack`: p95 under 50 ms.
- First preview result: p50 under 500 ms, p95 under 1.5 s when provider is healthy.
- `final_ack`: p95 under 100 ms after durable enqueue.
- Final result: p50 under 1 s, p95 under 3 s when provider is healthy.
- Reconnect to `ready`: p95 under 500 ms excluding authentication refresh.
- No preview older than the newest known revision may be emitted.

## 15. Acceptance tests

Backend implementation is ready when all tests pass:

1. Send preview revisions 1...20 rapidly. Only the newest available revision is emitted after supersession; no old result is emitted afterward.
2. Disconnect while an old preview is running, reconnect, send a newer revision, and verify the old connection cannot emit to the new one.
3. Send the same final request five times. Exactly one logical provider job/context entry is created and the same final result is returned.
4. Disconnect after `final_ack` and before completion. Resume and receive the final result without resending source text.
5. Restart the backend worker after `final_ack`. The final still completes.
6. Force preview provider timeout. The next preview succeeds without closing the WebSocket or affecting finals.
7. Force final provider timeout. Backend retries and preserves the final across reconnect.
8. Complete finals out of order internally. Client emissions remain in source turn order.
9. Reuse a session from another account. Backend rejects it.
10. Send malformed JSON and unsupported message types. Backend returns structured errors and remains usable when safe.
11. Send previews above the rate limit. Backend coalesces them while finals continue normally.
12. Run a 90-minute session with periodic disconnects and verify no duplicate/missing finals and bounded memory.

## 16. Migration plan

1. Implement v2 alongside the existing endpoints.
2. Add backend feature flag `live_translation_v2_macos` by account or percentage rollout.
3. Test with a protocol simulator before integrating macOS.
4. Connect macOS development builds to v2.
5. Compare v1/v2 latency and error metrics.
6. Roll out macOS gradually.
7. Keep Web and Windows on v1 until their clients explicitly implement v2.
8. After stability is proven, migrate other clients without changing v2 semantics.

## 17. Optional STT v2 adjustments

The current Deepgram proxy may remain unchanged if it transparently forwards query parameters and messages. If a v2 STT endpoint is introduced, it should:

- accept 20–100 ms linear16 audio blocks;
- pass through `is_final`, `speech_final`, `UtteranceEnd`, timestamps, request IDs, and errors unchanged;
- support `interim_results=true`, `endpointing=300`, `utterance_end_ms=1000`, and `vad_events=true`;
- send Deepgram KeepAlive only when no audio is flowing;
- expose connection/audio/transcript cursor timing for latency diagnostics;
- never couple Deepgram reconnect state to translation reconnect state.
